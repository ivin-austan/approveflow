# ApproveFlow Database Design

## Document status

- Phase: 1 - logical database design
- Status: awaiting approval
- Database: PostgreSQL using Drizzle schemas and generated migrations

## Conventions

- Use UUID primary keys generated by trusted application/database code.
- Use `snake_case` database names and map them to TypeScript domain names.
- Use `timestamptz` for every timestamp.
- Use `numeric` for money.
- Every tenant-owned table includes `organization_id`, even when derivable from
  a parent record.
- Use foreign keys, unique constraints, and checks to reinforce application
  validation.
- Never delete or update audit events through normal application operations.
- Repositories and database modules are the only standard database-access
  boundary.

## Enumerations

Logical enum values include:

```text
membership_status: INVITED | ACTIVE | SUSPENDED
workflow_status: ACTIVE | ARCHIVED
workflow_version_status: DRAFT | PUBLISHED | RETIRED
completion_policy: ANY | ALL
assignment_type: MEMBERSHIP | ROLE | DEPARTMENT_ROLE |
                 REQUESTER_MANAGER | FORM_FIELD_USER
request_status: DRAFT | SUBMITTED | IN_REVIEW | RETURNED |
                APPROVED | REJECTED | CANCELLED
stage_instance_status: WAITING | ACTIVE | COMPLETED | REJECTED |
                       RETURNED | AUTO_APPROVED | SKIPPED
approval_task_status: WAITING | PENDING | APPROVED | REJECTED |
                      RETURNED | SKIPPED
decision_actor_type: MEMBERSHIP | SYSTEM
escalation_action: NOTIFY | RETURN_TO_INITIATOR
pdf_artifact_status: PENDING | GENERATING | READY | FAILED | DELETED
delivery_status: PENDING | SENDING | DELIVERED | FAILED |
                 PERMANENTLY_FAILED

```

PostgreSQL enums or constrained text may be selected during implementation.
Either choice must produce exhaustive TypeScript handling and migrations for
contract changes.

## Identity, organization, and authorization tables

### `users`

- `id` UUID primary key
- `email` normalized case-insensitive unique value
- `full_name`
- `password_hash`
- `status`
- `email_verified_at` nullable
- `created_at`, `updated_at`

### `organizations`

- `id` UUID primary key
- `slug` unique
- `name`
- `status`
- `created_at`, `updated_at`

### `departments`

- `id` UUID primary key
- `organization_id`
- `name`
- `code`
- `status`
- `created_at`, `updated_at`
- Unique `(organization_id, name)` for active naming rules
- Unique `(organization_id, code)`; codes are normalized and restricted to
  numbering-safe characters

### `memberships`

- `id` UUID primary key
- `organization_id`
- `user_id`
- `reporting_manager_membership_id` nullable
- `status`
- `created_at`, `updated_at`
- Unique `(organization_id, user_id)`

`membership_departments` contains `organization_id`, `membership_id`,
`department_id`, `is_default`, and timestamps. It has a unique membership/
department pair and at most one default department per membership. A member may
belong to multiple departments, but each document has exactly one validated
originating department.

The manager membership and every department must belong to the same
organization. Self-management cycles and longer reporting cycles are rejected
by application validation; a recursive query may be used for cycle detection if
justified and tested.

### `roles`, `permissions`, `role_permissions`, `membership_roles`

- Roles are organization-owned and have an organization-unique name.
- Permissions use stable system-defined keys.
- Role-permission and membership-role joins use composite uniqueness.
- Same-organization composite foreign keys prevent cross-tenant role grants.

### `invitations`

- `id`, `organization_id`
- `email`, `full_name`
- `token_hash`
- `status`, `expires_at`, `accepted_at` nullable
- `invited_by_membership_id`
- `created_at`, `updated_at`

Invitation roles use `invitation_roles(invitation_id, role_id,
organization_id)`. Invitation departments use
`invitation_departments(invitation_id, department_id, organization_id,
is_default)`. Only a hash of the invitation secret is stored.

## Document types, calendars, and numbering

### `document_types`

- `id`, `organization_id`
- `name`, `code`, `status`
- `business_calendar_id`
- `number_format`, using only allowlisted components
- `sequence_padding` default 6
- `approved_pdf_retention_years` default 7 within platform bounds
- `approved_pdf_field_policy` validated allowlist/exclusion policy
- `automatic_approval_enabled` boolean default false
- `automatic_approval_duration` integer nullable
- `automatic_approval_duration_unit` nullable (`BUSINESS_HOURS` or
  `BUSINESS_DAYS`)
- `created_at`, `updated_at`
- Unique `(organization_id, name)` and `(organization_id, code)`

Document-type administration controls automatic approval; no separate elevated
automatic-approval permission is required. A published workflow version
snapshots the effective setting for reproducible runtime behavior.

`document_type_dashboard_configs` contains `id`, `organization_id`,
`document_type_id`, validated default-visible system columns, explicitly
non-sensitive form-field columns, default sort/filter settings, `revision`, and
timestamps. It is unique by document type. Configuration never grants row or
field access; authorization policies remain authoritative.

`document_legal_holds` contains `id`, `organization_id`, `request_id`, reason,
actor membership, placed/released timestamps, and audit linkage. An active hold
blocks artifact and document retention deletion.

### Business calendar tables

- `business_calendars`: organization, name, IANA timezone, revision, status,
  timestamps.
- `business_calendar_work_periods`: organization, calendar, weekday, local start
  time, local end time, timestamps.
- `business_calendar_holidays`: organization, calendar, local date, name,
  optional working override, timestamps.

Each organization has one default calendar. Due, reminder, escalation, and
automatic-approval timestamps are calculated in business time and stored as UTC
`timestamptz`. Runtime records snapshot the calendar ID/version and calculated
deadline.

### `document_number_sequences`

- `id`, `organization_id`
- `department_id`, `document_type_id`
- `sequence_year` integer
- `last_value` bigint
- `created_at`, `updated_at`
- Unique `(organization_id, department_id, document_type_id, sequence_year)`

The submission transaction atomically creates or locks this row, increments
`last_value`, and renders the number from snapshotted codes. Sequence values are
never decremented or reset within the same scope.

### `document_number_allocations`

- `id`, `organization_id`
- `request_id` nullable foreign key using `ON DELETE SET NULL`
- `request_id_snapshot` UUID not null
- `department_id`, `document_type_id`, `sequence_year`, `sequence_value`
- `department_code_snapshot`, `document_type_code_snapshot`
- `format_snapshot`, `document_number`
- `allocated_at`
- Unique `(organization_id, document_number)`
- Unique `(organization_id, department_id, document_type_id, sequence_year,
  sequence_value)`
- Unique `(request_id_snapshot)`

Allocations are append-only and survive any later permitted deletion or
anonymization of a document, preventing reuse. A rolled-back submission creates
neither an allocation nor a consumed sequence value.

Sequence rows are never deleted or decremented through normal application
operations. Department and document-type codes that appear in allocations are
reserved to their original entity, preventing a different entity from later
recreating an old rendered-number namespace.

## Workflow definition tables

### `workflows`

- `id`, `organization_id`
- `document_type_id`
- `name`, `description`
- `status`
- `current_published_version_id` nullable
- `created_by_membership_id`
- `created_at`, `updated_at`
- Unique `(organization_id, document_type_id)` so each document type owns one
  versioned workflow in the initial release

### `workflow_versions`

- `id`, `organization_id`, `workflow_id`
- `version_number`
- `status`
- `revision` for draft optimistic concurrency
- `allow_no_stage_automatic_approval` boolean default false
- `automatic_approval_enabled` boolean default false
- `automatic_approval_duration` integer nullable
- `automatic_approval_duration_unit` nullable
- `business_calendar_id`
- `approved_pdf_field_policy` immutable publication snapshot
- `allow_requester_self_approval` boolean default false
- `published_by_membership_id` nullable
- `published_at` nullable
- `created_at`, `updated_at`

Constraints:

- Unique `(organization_id, workflow_id, version_number)`.
- Partial unique index allowing at most one draft per workflow.
- Publication metadata is present only for published versions.
- Application repositories refuse all updates to published versions.
- Automatic-approval and calendar values are copied from the document type when
  a version is published and remain immutable with that version.

### Form-definition tables

- `form_sections`: organization, version, stable key, name, description,
  position, timestamps.
- `form_fields`: organization, version, section, stable key, type, label,
  description, required flag, position, validated type-specific `config`,
  timestamps.
- `field_options`: organization, field, stable value, label, position,
  timestamps.
- `field_conditions`: organization, version, target field, effect, validated
  condition AST, timestamps.

Stable field IDs are referenced by conditions and `FORM_FIELD_USER`
assignments. Positions are unique within their parent and contiguous after a
draft save.

### `workflow_stages`

Required columns:

- `id` UUID primary key
- `organization_id` UUID not null
- `workflow_version_id` UUID not null
- `name` text not null
- `description` text nullable
- `instructions` text nullable
- `position` integer not null
- `completion_policy` (`ANY` or `ALL`) not null
- `due_duration` integer nullable
- `due_duration_unit` nullable (`BUSINESS_HOURS` or `BUSINESS_DAYS`)
- `business_calendar_id` nullable; otherwise inherit the version snapshot
- `activation_condition` validated JSONB nullable
- `created_at`, `updated_at` as `timestamptz`

Constraints and indexes:

- Unique `(workflow_version_id, position)`.
- Check `position >= 1`.
- Check `due_duration > 0` and require a unit when present.
- Composite foreign key guarantees the version and stage share an organization.
- Index `(organization_id, workflow_version_id, position)`.

There is deliberately no `is_final` definition column. The last applicable
stage is a runtime fact.

### `stage_approvers`

Required columns:

- `id` UUID primary key
- `organization_id` UUID not null
- `workflow_stage_id` UUID not null
- `assignment_type` not null
- `membership_id` nullable
- `role_id` nullable
- `department_id` nullable
- `form_field_id` nullable
- `invitation_id` nullable for draft-only pending-person selection
- `display_order` integer not null
- `created_at` as `timestamptz`

Reference rules:

| Assignment type | Required references | Forbidden references |
|---|---|---|
| `MEMBERSHIP` | Exactly one of active `membership_id` or draft-only `invitation_id` | role, department, field |
| `ROLE` | `role_id` | membership, invitation, department, field |
| `DEPARTMENT_ROLE` | `department_id` and `role_id` | membership, invitation, field |
| `REQUESTER_MANAGER` | None | membership, invitation, role, department, field |
| `FORM_FIELD_USER` | `form_field_id` | membership, invitation, role, department |

Database check constraints enforce null-shape rules. Application validation
enforces active status, field type, draft-only invitation use, and tenant
ownership. Composite foreign keys should enforce organization consistency
where practical.

`ROLE` and `DEPARTMENT_ROLE` resolve every matching active membership at
submission. `FORM_FIELD_USER` is enabled in the initial MVP and must reference a
member-selector field populated by the document initiator; its value is
revalidated as an active same-tenant membership during submission.

Unique `(workflow_stage_id, display_order)` preserves builder order. Duplicate
equivalent assignments within one stage are rejected by application validation
and supporting partial unique indexes where feasible.

### Reminder and escalation definitions

`stage_reminder_rules` contains organization, stage, sequence, business-time
offset relative to activation or due time, recipient policy, and timestamps.

`stage_escalation_rules` contains organization, stage, sequence, business-time
offset, and an action restricted to `NOTIFY` or `RETURN_TO_INITIATOR`.
Notification recipients must be verified organization memberships or safe
organization-defined roles. `RETURN_TO_INITIATOR` changes the request to
`RETURNED`, closes the current round, and restores responsibility to the
original requester; it does not create an approval task for the requester.

Publication validates that offsets and targets are coherent with the stage due
duration.

## Request runtime tables

### `requests`

- `id`, `organization_id`
- `document_number` nullable while draft and immutable after submission
- `temporary_reference` nullable and clearly non-final
- `document_type_id`, `originating_department_id`
- `workflow_id`, `workflow_version_id`
- `requester_membership_id`
- `status`
- `current_approval_round_id` nullable
- `current_stage_instance_id` nullable
- `revision`
- `submitted_at`, `resolved_at` nullable
- `created_at`, `updated_at`

`document_number` has a unique `(organization_id, document_number)` constraint
when non-null. The originating department must be one of the initiator's active
membership departments at submission. Indexes support
organization/status/date, requester/date, document type/date, workflow/date,
and cursor pagination.

### `request_answers`

- `id`, `organization_id`, `request_id`, `form_field_id`
- `value` validated JSONB
- `created_at`, `updated_at`
- Unique `(request_id, form_field_id)`

The value schema is determined by the immutable field definition. Sensitive
values are not copied to logs or audit metadata.

### `approval_rounds`

- `id`, `organization_id`, `request_id`
- `round_number`
- `status`
- `started_at`, `completed_at` nullable
- `created_at`
- Unique `(request_id, round_number)`

Rounds preserve earlier paths and decisions when a returned request is
resubmitted. Every resubmission creates a new round, reevaluates the full
applicable journey and current assignees, and restarts from its first applicable
stage.

### `request_stage_instances`

Each applicable stage in a round is snapshotted with:

- `id`, `organization_id`
- `request_id`, `approval_round_id`
- `workflow_stage_id`
- `stage_name`, `stage_description`, `stage_instructions`
- `stage_position`
- `applicable_level` such as 1 through the number of applicable stages
- `completion_policy`
- `is_final_applicable` boolean
- `status`
- `due_duration` nullable
- `due_duration_unit` nullable
- `business_calendar_id_snapshot`
- `due_at` nullable
- `automatic_approval_due_at` nullable
- `resolved_approvers_snapshot` JSONB containing safe membership IDs, names,
  emails, role labels, department labels, and assignment sources
- Validated condition outcome metadata that does not expose sensitive answers
- `activated_at`, `completed_at` nullable
- `created_at`

Constraints:

- Unique `(approval_round_id, applicable_level)`.
- Exactly one final applicable instance per non-automatic-approval round.
- At most one `ACTIVE` stage per active round, enforced transactionally and with
  a partial unique index where practical.
- A final marker is immutable after round creation.

The stage snapshot supports durable historical rendering. Associated task rows
remain the authoritative relational identities; snapshot JSON never authorizes
an action.

### `approval_tasks`

- `id`, `organization_id`
- `request_id`, `approval_round_id`, `request_stage_instance_id`
- `assignee_membership_id` UUID not null
- `status`
- `approver_display_name_snapshot`
- `approver_email_snapshot`
- `approver_role_labels_snapshot`
- `approver_department_labels_snapshot`
- `assignment_type_snapshot`
- `assignment_label_snapshot`
- `decision_comment` nullable
- `decided_at` nullable
- `supersedes_task_id` nullable for an explicit reassignment replacement
- `closed_reason` nullable, including `REASSIGNED`
- `lock_version`
- `created_at`, `updated_at`

The task's identity is its UUID plus a specific membership reference. Email is
never identity. A unique constraint on `(request_stage_instance_id,
assignee_membership_id)` deduplicates a member resolved through multiple rules.

Task status begins `WAITING`; all tasks in the active stage become `PENDING`
simultaneously. The next stage activates only after the current stage completes.

Role, department, manager, and membership changes never update runtime tasks
automatically. Explicit reassignment closes the original pending task with
reason `REASSIGNED`, inserts one linked task for a verified active same-tenant
membership, appends an audit event, and creates an outbox notification in one
transaction. Historical assignee snapshots remain unchanged.

### `approval_decisions`

- `id`, `organization_id`
- `request_id`, `approval_round_id`, `request_stage_instance_id`
- `approval_task_id` nullable for a system decision
- `actor_type` (`MEMBERSHIP` or `SYSTEM`)
- `actor_membership_id` nullable and required only for membership decisions
- `decision` (`APPROVED`, `REJECTED`, `RETURNED`, or `AUTO_APPROVED`)
- `comment` nullable
- `policy_snapshot` JSONB nullable for system automatic approval
- `decided_at`

A system automatic approval is a stage-level decision and never impersonates a
member. It sets the stage to `AUTO_APPROVED`, skips remaining pending tasks, and
is rendered as `System Auto-Approved` in the audit timeline. A unique operation
or deduplication constraint prevents the same stage deadline from producing two
system decisions.

### Comments, idempotency, audit, outbox, and notification tables

- `request_comments`: tenant, request, round/stage/task references, actor,
  comment type, body, timestamp.
- `idempotency_records`: tenant, actor, operation, key, canonical request hash,
  state, response code/body, expiry, timestamps. Unique by tenant, actor,
  operation, and key.
- `audit_events`: tenant, actor, entity type/id, event type, safe metadata,
  correlation ID, `occurred_at`. Append-only.
- `outbox_events`: tenant, aggregate, event type, versioned typed payload,
  deduplication key, status, availability, attempts, timestamps.
- `notifications`: tenant, recipient membership, channel, outbox/event link,
  delivery state, provider-safe identifiers, timestamps.
- `scheduled_stage_actions`: tenant, stage instance, rule snapshot, action type,
  due time, status, deduplication key, timestamps.

An index on `(status, available_at)` for pending outbox and scheduled rows
supports workers. Delivery payloads contain no raw refresh/access credentials.

### `approved_document_artifacts`

- `id`, `organization_id`
- `request_id`, `approval_round_id`, `final_approval_audit_event_id`
- `artifact_type` fixed to `APPROVED_STATEMENT_PDF` initially
- `renderer_version`
- `status` (`PENDING`, `GENERATING`, `READY`, `FAILED`, or `DELETED`)
- `storage_key` nullable and tenant-scoped
- `source_manifest_sha256`
- `content_sha256` nullable
- `mime_type` fixed to `application/pdf`
- `byte_size` nullable
- `page_count` nullable
- `generation_timestamp` fixed when the artifact row is created
- `attempt_count`, `max_attempts` default 5
- `last_error_code`, `next_attempt_at`, `retry_exhausted_at` nullable
- `lease_owner`, `lease_expires_at` nullable
- `generated_at` nullable
- `retention_expires_at`, `deleted_at` nullable
- `created_at`, `updated_at`
- Unique `(organization_id, request_id, approval_round_id,
  final_approval_audit_event_id, artifact_type, renderer_version)`

The row is inserted as `PENDING` in the final-approval transaction. PDF bytes
are generated and stored only after commit. Storage uses a deterministic key so
a retry cannot create multiple logical artifacts. `content_sha256` supports
integrity verification and traceability.

Allowed transitions are:

- `PENDING -> GENERATING`
- `GENERATING -> READY | FAILED`
- `GENERATING -> PENDING` after an expired lease is recovered
- `FAILED -> PENDING` for an allowed automatic or authorized manual retry
- `READY | FAILED -> DELETED` through retention processing

`READY` content is immutable. `DELETED` is terminal. Five automatic attempts use
jittered backoff of approximately 1 minute, 5 minutes, 15 minutes, 1 hour, and 6
hours. `approved_pdf.retry` can reset a retry-exhausted `FAILED` row to `PENDING`
without inserting another artifact; the action is rate-limited and audited.
Any later valid approval round creates a new artifact row and never overwrites a
prior round's artifact.

`artifact_generation_attempts` is append-only and contains organization,
artifact, attempt number, worker/job identifiers, renderer version, start/end
timestamps, outcome, safe error code, and observed output hash/size. It is unique
by artifact and attempt number.

### `document_delivery_records`

- `id`, `organization_id`
- `request_id`, `approved_document_artifact_id`
- `recipient_membership_id`
- `recipient_kind` (`INITIATOR` or `CONFIGURED_RECIPIENT`)
- `recipient_name_snapshot`, `recipient_email_snapshot`
- `recipient_email_verified_at_snapshot`
- `delivery_type` fixed to `FINAL_APPROVAL_EMAIL` initially
- `delivery_mode` (`ATTACHMENT` or `SECURE_LINK`)
- `attachment_omission_reason` nullable, including `SIZE_LIMIT`
- `template_version`, `deduplication_key`
- `status` (`PENDING`, `SENDING`, `DELIVERED`, `FAILED`, or
  `PERMANENTLY_FAILED`)
- `provider_message_id` nullable
- `provider_idempotency_key`
- `attempt_count`, `max_attempts` default 8
- `last_error_code`, `failure_class`, `next_attempt_at`, `retry_exhausted_at`
  nullable
- `reconciliation_required_at`, `last_reconciled_at` nullable
- `lease_owner`, `lease_expires_at` nullable
- `provider_accepted_at`, `delivered_at`, `bounced_at` nullable
- `manually_reopened_by_membership_id`, `manually_reopened_at` nullable
- `created_at`, `updated_at`
- Unique `(organization_id, deduplication_key)`

One logical delivery is created per final-approval event, canonical artifact,
recipient membership, recipient kind, and template version. Retries update that
row. For the initiator, the current verified account email is captured at final
approval only when the organization membership is active. Configured recipients
receive `SECURE_LINK`; the initiator receives `ATTACHMENT` unless the provider
limit is exceeded, in which case the row records `SECURE_LINK` and `SIZE_LIMIT`.
Configured recipients are likewise resolved only to active memberships with
current verified account emails.

Before submission, the worker revalidates active membership and confirms that
the snapshotted email remains the current verified address. Failure sets
`PERMANENTLY_FAILED` without sending. An authorized reopen may update the same
record's recipient snapshot to the restored current verified address and records
the actor and timestamp.

Allowed transitions are:

- `PENDING -> SENDING`
- `SENDING -> DELIVERED | FAILED | PERMANENTLY_FAILED`
- `SENDING -> SENDING` while provider acceptance is reconciled
- `FAILED -> PENDING` for an allowed automatic or manual retry
- `DELIVERED -> PERMANENTLY_FAILED` after a later hard-bounce/rejection callback
- `PERMANENTLY_FAILED -> PENDING` only through an authorized audited reopen after
  the cause is corrected

Eight automatic attempts use jittered backoff of approximately 1 minute, 5
minutes, 15 minutes, 1 hour, 6 hours, 12 hours, 24 hours, and 48 hours. Unknown
provider acceptance remains `SENDING` with reconciliation metadata; it is not
blindly resubmitted. Ineligible recipients, hard bounces, definitive rejection,
and retry exhaustion become `PERMANENTLY_FAILED` and stop automatic retries.
Provider idempotency keys close the send/acknowledgement crash window where the
provider supports them.

`document_delivery_attempts` is append-only and contains organization, delivery,
attempt number, provider request/idempotency identifiers, start/end timestamps,
outcome (`ACCEPTED`, `FAILED`, `UNKNOWN`, `RECONCILED`, `BOUNCED`, or
`REJECTED`), and a safe error code. It is unique by delivery and attempt number
and stores no email body or attachment bytes.

### `artifact_access_grants`

- `id`, `organization_id`, `approved_document_artifact_id`
- `granted_to_membership_id`
- `purpose` (`VIEW`, `PRINT`, `DOWNLOAD`, or `EMAIL_LINK`)
- `token_hash`, `expires_at`, `max_uses`, `use_count`, `revoked_at` nullable
- `created_at`, `last_used_at` nullable

Grants are created only after full document authorization. Raw tokens are never
stored. Default lifetime is five minutes and use is purpose/audience-bound.
Where the API streams bytes directly, no object URL is returned. Every view,
print request, download, grant creation/use, retry, generation, deletion, and
email transition also creates an append-only audit event.

### Artifact retention

Canonical PDFs inherit the document type's retention policy, defaulting to seven
years after final approval. A legal hold prevents expiry. Retention processing
deletes private object bytes, verifies absence, transitions the row to `DELETED`,
and retains minimum metadata and the audit trail according to policy. Encrypted
backups follow the same expiry schedule plus a documented backup purge window.
Restore procedures verify organization scope and stored SHA-256 hashes before an
artifact is served.

## Publication transaction

Publication locks the workflow and draft version, checks expected revision,
runs complete structural and tenant validation, marks the version published,
updates the workflow's current published reference, appends an audit event, and
commits. It does not send invitation or publication email inside the
transaction.

## Submission transaction

Submission locks the request and idempotency record; validates its one
originating department, state, answers, document type, and workflow version;
atomically increments the organization/department/document-type/year sequence;
inserts the permanent number allocation; appends the durable `SUBMITTED` audit
event; evaluates applicable stages; resolves all assignment rules; creates a
round, stage instances, and membership-backed tasks; marks the runtime final
stage; activates the first stage; sets current status to `IN_REVIEW`; calculates
business-calendar deadlines; appends audit/outbox records; stores the response;
and commits.

The UUID remains the primary key. The generated document number is immutable,
and the append-only allocation prevents reuse after rejection, cancellation, or
later deletion. A transaction rollback allocates neither the number nor the
sequence value. `SUBMITTED` remains in audit history but is not a resting current
status.

If no stage applies and `allow_no_stage_automatic_approval` is false, or any
applicable stage resolves to no active approver, all changes roll back. When
no-stage automatic approval is allowed, submission records the system action and
sets current status directly to `APPROVED` in the same transaction.

## Decision transaction and concurrency

Decision processing locks records in a stable order or uses conditional atomic
updates. It verifies that the task is pending in the current round and assigned
to the actor, records one decision, computes the completion policy, advances at
most once, and writes audit/outbox/idempotency rows before commit.

Concurrent approvals in an `ANY` stage can result in only one winning stage
completion. Later contenders receive the stored idempotent result or a typed
stale-action conflict. `ALL` completion is calculated from locked current task
state.

A scheduled automatic-approval transaction locks the active stage and request,
verifies the snapshotted business-calendar deadline has passed and the stage is
still incomplete, records a system decision and `System Auto-Approved` audit
event, skips remaining tasks, and activates the next stage or approves the
request. It writes the same next-approver event as a human stage completion or,
when final, the same canonical-PDF generation event.

An escalation with `RETURN_TO_INITIATOR` immediately changes the request to
`RETURNED`, closes remaining round tasks, appends the audit event, and queues an
initiator notification. It does not insert an initiator approval task.

## Final approval, PDF, and delivery transactions

The final-stage transaction marks the request approved, writes the immutable
approval and audit records, inserts exactly one `PENDING` approved artifact,
snapshots the initiator's current verified email and configured recipients into
logical delivery records, and writes one `PDF_GENERATION_REQUESTED` outbox event
before commit. An ineligible initiator delivery is inserted as
`PERMANENTLY_FAILED`; eligible deliveries remain `PENDING`. The transaction does
not render, store, or email PDF bytes.

After generating and storing the PDF, a short database transaction conditionally
changes the artifact from `GENERATING` to `READY`, records its hash and size,
writes email outbox events for the existing eligible delivery records. If
generation fails, the artifact becomes `FAILED` with a retry schedule while the
request and pending delivery records remain unchanged and unsent.

The email worker claims one delivery row using a lease. Provider acceptance
records `DELIVERED` and the provider message ID; a retryable confirmed failure
records `FAILED` and `next_attempt_at`; ambiguous timeouts remain `SENDING` for
reconciliation. Unique keys prevent duplicate logical artifacts, outbox events,
and deliveries. A manual retry or reopen resets the existing failed record
rather than inserting another delivery.

## Migration policy

- Drizzle schema definitions are the source of migration generation.
- Generated migrations are reviewed and committed.
- Schema push is never used against production.
- Destructive migrations require explicit approval and a recovery plan.
- Constraints are introduced with deployment-safe sequencing when existing
  data is present.
